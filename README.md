# fail2ban-center

Централизованное управление fail2ban на произвольном числе серверов из одного веб-интерфейса —
**без входящего доступа на управляемые хосты**. Каждый управляемый сервер сам, исходящим
HTTPS (или через WireGuard-туннель), раз в минуту стучится в центр за задачами: забанить,
разбанить, обновить игнор-лист — а не наоборот, как в классических SSH-based решениях.

Полное ТЗ с обоснованием архитектурных решений — [`docs/TZ.md`](docs/TZ.md). Этот README —
практическое руководство: что это, как ставится, чем управляется, сколько потребляет.

## Почему не SSH

Соседний, более ранний вариант того же проекта — [`fail2ban-sync-host`](../fail2ban-sync-host) —
делает то же самое, но центр сам ходит по SSH на каждый управляемый сервер. Это отлично
работает, пока у всех серверов есть входящий SSH-доступ. Как только среди них появляются
хосты за NAT/CGNAT, без белого IP, за файрволом, который режет входящие порты — SSH-модель
упирается в стену. **fail2ban-center** переворачивает направление: агент сам инициирует
соединение, поэтому подходит для любого хоста, у которого есть хоть какой-то исходящий доступ
в интернет.

За это платится точностью реакции: между "нажал кнопку в UI" и "применилось на сервере"
проходит время до одного интервала чекина (по умолчанию 60 секунд), а не сразу, как при SSH.
Для fail2ban это осознанно приемлемый компромисс — это не средство реалтайм-защиты, а
инструмент управления баном, где секунды не критичны.

## Архитектура

```
 [Агент 1] --HTTPS/WireGuard (исходящий)--\
 [Агент 2] --HTTPS/WireGuard (исходящий)--- [Центр: REST API + БД + Web UI] <-- браузер
 [Агент N] --HTTPS/WireGuard (исходящий)--/
```

- **Центр** — один Flask/gunicorn-процесс + SQLite. Никуда сам не ходит, только принимает
  входящие запросы от агентов (Bearer-токен, свой на каждого) и от браузера администратора
  (логин/пароль, сессия).
- **Агент** — непривилегированный короткоживущий процесс (Python, только стандартная
  библиотека — pip/venv на управляемом хосте не нужен), запускается `systemd timer`, не
  демон. Каждый тик: чекин → выполнение полученных задач через `sudo` к одному фиксированному
  root-скрипту → следующий тик отправляет результаты. Реальные операции над fail2ban —
  только через `fail2ban-client`, ничего больше на хост не устанавливается и не открывается.
- Модель привилегий одна в один как в SSH-варианте: root-доступ агента ограничен ОДНИМ
  скриптом (`f2b-agent-helper`) с фиксированным набором подкоманд, каждый аргумент
  (IP/имя джейла) валидируется дважды — и на стороне агента, и внутри самого скрипта.

## Функции

- **Джейлы — автообнаружение, без ручного ввода.** Ни при регистрации агента в панели, ни
  при установке (`install_agent.sh`) список джейлов вводить не нужно — агент сам смотрит
  `fail2ban-client status` (плюс реальный `bantime` каждого), сообщает центру на каждом
  чекине, и центр сам добавляет новые в список разрешённых для этого агента. По умолчанию
  только добавляет (случайный сбой обнаружения не должен молча снести джейл) — кнопка
  «Пересинхронизировать джейлы» на странице агента запускает разовую полную сверку, которая
  ещё и убирает джейлы, которых на хосте больше нет.
- **Баны** — по джейлу, включая служебный `agent-permanent-ban` (bantime=-1, "забанить
  навсегда") — управляется центром автоматически, добавляется в разрешённые джейлы агента
  без участия администратора. У кнопки «Забанить навсегда» есть чекбокс «сразу на все
  агенты» — банит через тот же механизм, что и автоматическая эскалация глобального
  блок-листа (см. ниже), не отдельным путём.
- **Игнор-листы** — временный (TTL, ведёт центр) и постоянный (персистентный, пишется в
  jail.d-конфиг агентом, объединяется с уже настроенным на хосте `[DEFAULT] ignoreip`, не
  затирая его — базовый ignoreip хоста виден в панели для справки). Добавление —
  сразу несколькими IP/сетями (CIDR) через запятую, построчно или файлом, а не по одному.
- **Глобальный блок-лист** — если один IP банится на одном агенте N раз подряд (порог
  настраивается), банится сразу на всех агентах. С "липкой" памятью (повторное появление
  ранее разбаненного вручную IP снова банит его везде) и приоритетом за ручным разбаном
  прямо на сервере (если админ снял бан локально — центр это видит и снимает бан
  ВЕЗДЕ, полностью забывая IP). Есть свой игнор-лист ("это не бот") с импортом/экспортом
  файлом. Ту же таблицу пополняет и ручной "бан навсегда везде" (см. выше) — страница
  «Блок-лист» показывает оба источника вместе.
- **Бан сети Tor** — список exit-нод скачивает центр (не агенты — упрощение относительно
  SSH-варианта, где скачивание упиралось в блокировки с части хостов), раздаёт всем агентам
  diff'ом. Источник списка — URL (опционально через прокси, например SOCKS5, если сеть
  центра не пускает напрямую) **или** локальный файл на диске центра, если список туда
  кладёт что-то внешнее (cron/rsync) — настраивается в «Настройках».
- **Просмотр логов** — три режима на выбор в настройках:
  - `local` — агент сам докачивает только новые байты лога fail2ban на каждом чекине,
    центр хранит их локально. Работает сразу, ничего внешнего не нужно.
  - `graylog` — если у вас уже есть Graylog, центр обращается к его REST API напрямую и
    показывает результат во вкладке "Лог". Пошаговая настройка (GELF TCP input, токен) —
    прямо в разделе "Настройки" центра и в [`docs/TZ.md` §3.9](docs/TZ.md).
  - `none` — выключено.
- **VPN-сеть (WireGuard, опционально)** — для агентов без стабильного публичного доступа
  до центра: `manage.py vpn-init` поднимает на центре WG-хаб (звезда, агенты видят только
  центр, не друг друга), `install_agent.sh --setup-vpn` генерирует ключ на агенте — публичный
  ключ агента администратор один раз вносит через веб-панель (страница агента), в ответ
  получает данные для завершения настройки на самом агенте. После этого весь протокол
  агент↔центр идёт через зашифрованный туннель, публичного раскрытия API центра не требуется
  вообще.
- **Группы серверов**, **роли admin/operator**, **аудит-лог** — как и в SSH-варианте,
  функционально не отличается.
- **Интерфейс** — визуально по образцу SSH-варианта: над каждой страницей общая полоса
  вкладок для навигации по группам/подгруппам вглубь до конкретного агента; на странице
  агента баны по джейлам и просмотр лога — тоже вкладки в одной строке (переключение
  мгновенное, без перезагрузки страницы). Списки банов на вкладке ограничены 200 записями
  с пометкой "показаны последние N из M" — джейл вроде `agent-tor-block` может держать
  тысячи записей, инлайновый рендер всех сразу превращал бы страницу в многомегабайтный
  HTML.

## Установка центра

```bash
cd center
sudo deploy/install.sh install    # спросит порт, адрес прослушивания, пользователя сервиса
```

Слушает только на указанных адресах, снаружи — через reverse-proxy с TLS (пример —
`center/deploy/nginx-example.conf`) либо через SSH-туннель для доступа администратора,
как это было принято и в SSH-варианте:

```bash
ssh -L 8765:127.0.0.1:8765 <пользователь>@<хост_центра>
# затем http://127.0.0.1:8765 в браузере
```

Первый администратор создаётся интерактивно во время установки (или отдельно —
`venv/bin/python3 manage.py create-admin`).

## Подключение агента

В веб-интерфейсе центра: «Управление агентами» → «Добавить агента» — укажите только имя
(и, по желанию, группу). Джейлы указывать не нужно — они находятся сами на управляемом
хосте при установке и дальше поддерживаются актуальными каждым чекином (см. «Функции»
выше). Токен и готовая команда установки показываются сразу же. То же самое — через CLI:

```bash
venv/bin/python3 manage.py add-agent srv-42
```

На самом управляемом хосте (fail2ban там уже должен быть установлен и запущен):

```bash
sudo agent/install_agent.sh --center-url https://center.example.org --token <ТОКЕН> \
    --agent-name srv-42
```

Скрипт сам определяет пакетный менеджер (dnf/yum — REDOS/RHEL; apt-get — Ubuntu/Debian/ALT
Linux), доустанавливает python3 при необходимости, создаёт непривилегированного системного
пользователя, ставит узкое sudoers-правило на один root-скрипт, сам находит джейлы через
`fail2ban-client status` и переносит текущий `ignoreip` хоста в постоянный игнор агента
(чтобы не было окна без этой защиты до первого успешного чекина), проверяет, что всё реально
работает, и включает systemd-таймер. Никакого passwordless-sudo надолго не остаётся —
только на момент самой установки, если вообще требовался. Флаг `--jail имя:bantime` всё ещё
поддерживается, если для конкретного джейла нужно явно задать другой bantime — он тогда
имеет приоритет над автообнаруженным значением.

Для подключения через VPN вместо прямого HTTPS — добавьте `--setup-vpn` (подробности и полный
разбор сценария — [`agent/README.md`](agent/README.md)).

## Роли и права

| Действие | admin | operator |
|---|---|---|
| Просмотр банов/агентов/блок-листа/логов | ✅ | ✅ |
| Разбан (по джейлу, группой) | ✅ | ✅ |
| Временный игнор | ✅ | ✅ |
| Ручной бан | ✅ | ❌ |
| Постоянный игнор | ✅ | ❌ |
| Управление агентами/пользователями/группами/настройками/VPN | ✅ | ❌ |

Систему нельзя оставить без единого администратора — понижение роли или удаление последнего
`admin` заблокировано. Пароли — только через встроенный account-flow, минимум 6 символов.
Вход защищён от перебора (rate-limit на неудачные попытки, по IP, в памяти процесса).

## Модель прав (почему это относительно безопасно)

- Сам процесс агента не root, доступа к `fail2ban-client`/файлам fail2ban напрямую не имеет —
  всё идёт через `sudo /usr/local/sbin/f2b-agent-helper <фиксированная подкоманда>`.
- sudoers даёт NOPASSWD только на этот один root-скрипт, не на голый `fail2ban-client`.
- Скрипт-обёртка сам валидирует все аргументы (IPv4/имя джейла) — вторая, более авторитетная
  граница защиты поверх Python-стороны.
- Список разрешённых джейлов агент определяет сам на каждом запуске (живым
  `fail2ban-client status`, не тем, что когда-то прислал центр) — любая задача с джейлом,
  которого на хосте прямо сейчас нет, отклоняется агентом безусловно, даже если пришла с
  валидной авторизацией от центра. Центр не может заставить агента управлять джейлом,
  которого объективно не существует на этом хосте.
- Единственное, что скрипт сам пишет на диск управляемого хоста — идемпотентно генерируемые
  jail.d-файлы для служебных джейлов (`agent-permanent-ban`, `agent-tor-block`); запись всегда
  идёт через временный файл + `install`, с откатом к предыдущему состоянию, если
  `fail2ban-client reload` не удался.
- Токены агентов хранятся в БД центра только как HMAC-SHA256-хэш, сам токен — только в
  момент выдачи администратору.

## На чём это работает (стек)

- **Python 3** — весь код; центр разрабатывался под 3.11-3.13, агент написан только на
  стандартной библиотеке (совместим начиная с 3.9).
- **Flask** + **gunicorn** (`--workers 1 --threads 4 --worker-class gthread`) — веб-интерфейс
  и REST API центра. Один worker — намеренно: фоновый планировщик (TTL игнора, зависшие
  задачи, ежедневный Tor-пересбор) стартует один раз на процесс при импорте.
- **SQLite**, прямой SQL без ORM — единственное хранилище состояния центра.
- **systemd** — управляет и центром, и агентом (`timer`, не демон, у агента).
- **WireGuard** (опционально) — сеть агент↔центр, если выбран этот способ подключения вместо
  прямого HTTPS.
- **Graylog** (опционально) — просмотр логов, если выбран этот режим вместо локального кэша.
- **bash** — `f2b-agent-helper.sh`, единственное, что реально трогает fail2ban на управляемом
  хосте; зависит только от `coreutils` + `fail2ban-client`.
- **Фронтенд** — обычный HTML/CSS + немного inline JS (переключение светлой/тёмной темы),
  без сборки/бандлера/фреймворка, без внешних CDN.
- **pytest** — 16 тестов на бизнес-логику и протокол (БД временная, `tmp_path`), гоняются без
  реальной сети/fail2ban.

## Пределы масштабирования

Цифры ниже сняты с реальных развёртываний в процессе разработки (не синтетические оценки).

### Память и CPU

- **Центр** — резидентная память: master-процесс gunicorn ~20-25 МБ + один worker
  ~40-50 МБ (снято на реальном развёртывании с двумя агентами и ~1500 банов в самом
  крупном джейле — не синтетическая оценка), итого **~65-75 МБ** на весь процесс. Меньше,
  чем у SSH-варианта того же проекта — здесь нет постоянного пула SSH-соединений/paramiko.
- **Агент** — короткоживущий процесс, **пик ~22 МБ** резидентной памяти за время одного тика
  (доли секунды CPU), после чего процесс завершается полностью — между тиками на управляемом
  хосте не занято вообще ничего (ни памяти, ни CPU, ни файловых дескрипторов).
- Рекомендация для центра: **256-512 МБ** выделенной памяти с запасом для типичной установки;
  агенту отдельных ресурсов практически не требуется — он не резидентен.

### Сколько агентов может обслуживать один центр

Принципиально иначе, чем в SSH-варианте: там центр сам последовательно обходит все серверы
по SSH раз в 60 секунд, и это узкое место, растущее линейно с числом серверов. Здесь
инициатива у агентов — каждый чекин независимый HTTP-запрос, обрабатывается одним из потоков
gunicorn без ожидания остальных агентов. Практическое ограничение — не число агентов само по
себе, а конкурентная запись в SQLite (один писатель одновременно) при большом количестве
чекинов, приходящих в один и тот же момент.

- **Десятки-сотни агентов** при интервале чекина по умолчанию (60 с) — укладываются с большим
  запасом; чекины по своей природе не синхронизированы между агентами (у каждого свой момент
  запуска таймера), поэтому нагрузка размазана по всей минуте, а не приходит одним всплеском.
- Для очень больших инсталляций интервал чекина настраивается в большую сторону — тем самым
  снижается частота записи в БД без потери функциональности (только скорость реакции).
- Один нюанс на практике: центр пишет по одной SQL-транзакции на каждый новый бан в диффе
  чекина, поэтому *первый* чекин, где у джейла разом обнаруживается большой backlog (свежий
  Tor-blocklist на тысячи IP, агент восстановился после долгого простоя) может занимать
  ощутимое время — таймаут запроса на стороне агента специально поднят до 120 с именно под
  этот случай, обычные чекины укладываются в секунды.

### Сколько пользователей веб-панели одновременно

`gunicorn --workers 1 --threads 4` — до **4 запросов одновременно по-настоящему параллельно**
(Python отпускает GIL на время I/O — чтения SQLite, обращения к Graylog при просмотре лога),
пятый и далее встают в очередь на освободившийся поток. Для внутренней админ-панели (не
публичный сервис) это комфортно для **команды из 10-20 человек**, изредка нажимающих кнопки
не в одну секунду. `--threads` можно свободно увеличивать; `--workers` — нельзя без доработки
(единственный поток планировщика привязан к одному процессу при импорте).

## Известные ограничения

- Баны, временный игнор и глобальный блок-лист — только IPv4 (как и в исходном
  SSH-варианте). Постоянный игнор — исключение: принимает и IPv6/сети (валидируется через
  `ipaddress.ip_network`), потому что `[DEFAULT] ignoreip` в самом fail2ban изначально
  смешанный — центр не должен быть строже того, что host уже разрешает.
- Между действием в UI и его применением на сервере — задержка до одного интервала чекина
  (по умолчанию 60 с), плюс быстрее — через событийный канал уведомления о бане (доли секунды
  для факта "уже забанено где-то", не для доставки НОВЫХ команд с центра).
- WireGuard как транспорт — это обычный UDP-протокол; в сетях с активной DPI-блокировкой по
  сигнатуре протокола (не только по порту) может потребоваться дополнительная обфускация,
  которую этот проект не реализует.
- "Забанить навсегда" зависит от `banaction`, уже настроенного в `[DEFAULT]` целевого хоста —
  ответственность администратора конкретного сервера, не центра.

## Разработка

```bash
cd center
pip install -r requirements-dev.txt
pytest tests/ -v
```

Тесты не трогают реальную сеть/fail2ban — БД временная (`tmp_path`), модули переимпортируются
между тестами (у `db.py` есть модуль-level константы пути к БД).

воркэраунд конкретного бага, что-то, что удивило бы читателя). Не описывать словами то, что
