# Центр fail2ban-center

Веб-панель, API для агентов и SQLite в одном процессе (Flask под gunicorn). Работает только
по HTTPS: TLS завершает сам gunicorn, сертификат выпускает собственный CA центра. Сам центр
к серверам не подключается — только принимает запросы.

## Установка

Нужны: Linux с systemd, Python 3.9+, `openssl`, `rsync`, `sqlite3` (для `update`). Пакеты
python3/pip/venv установщик ставит сам (apt-get, dnf или yum).

```bash
cd center
sudo deploy/install.sh install
```

Установщик спрашивает:

1. **Порт** (по умолчанию 8766) и **пользователя сервиса** (`fail2ban-center`).
2. **Интерфейсы** — список реальных адресов хоста (`ip -4 addr`), можно несколько через
   пробел; `0` — только `127.0.0.1`. Веб-панель и агенты работают на одних и тех же адресах.
   Отдельный пункт — поднять VPN-сеть (WireGuard) для агентов без прямого доступа к центру.
3. **Reverse-proxy** перед центром — обычно нет (см. ниже).
4. **Первого администратора** — логин и пароль.
5. **Дополнительные адреса для сертификата** — если агенты обращаются к центру по адресу,
   которого нет на хосте (публичный IP за NAT, DNS-имя).

В конце печатаются адреса `https://…` и отпечаток CA (SHA-256) для подключения агентов.

### Команды

| Команда | Что делает |
|---|---|
| `install.sh install` | первая установка |
| `install.sh configure` | заново выбрать интерфейсы и порт, перевыпустить сертификат (CA тот же — агентам ничего менять не надо) |
| `install.sh update` | новая версия кода из текущего каталога; база копируется в `data/backup-*.sqlite3`, схема обновляется, настройки и юнит не меняются |
| `install.sh status\|start\|stop\|restart` | управление сервисом |
| `install.sh uninstall` | удалить; спросит, удалять ли базу и CA |

Ответы на вопросы можно подать через stdin (`printf '…' | sudo deploy/install.sh install`) —
для автоматизации.

## HTTPS и сертификат

- При первой установке создаётся CA: `/etc/fail2ban-center/tls/ca.crt` и `ca.key` (ключ
  читает только root, никуда не раздаётся). Дальше CA переиспользуется.
- От него выпускается `server.crt` (ключ `server.key` — `root:fail2ban-center`, 640). В
  сертификат (SAN) входят все выбранные адреса прослушивания **центра**, `127.0.0.1`,
  VPN-адрес центра, имя хоста и дополнительные адреса из вопроса установщика. В SAN —
  адреса **центра**, а НЕ агентов: собственный IP хоста-агента в сертификат не входит и для
  него не нужен; важен только адрес, по которому агент обращается к центру (`center_url`).
- **Добавление нового хоста (агента) сертификат НЕ перевыпускает** — установка агента серверный
  серт вообще не трогает (агент лишь качает `ca.crt`, пинит CA по отпечатку и проверяет серт
  центра по SAN). Поэтому:
    - если новый хост ходит на центр по адресу, который **уже** в SAN (напр. LAN- или
      VPN-адрес центра) — перевыпускать ничего не надо, просто ставите агент;
    - если новому хосту нужен **новый** адрес центра, которого в SAN ещё нет (подняли новый
      интерфейс/VPN на центре) — перевыпуск делается ВРУЧНУЮ на центре: `install.sh configure`
      (CA тот же → остальным агентам менять нечего). Либо адрес добавляется сразу при установке
      центра («дополнительные адреса для сертификата»).
  Если агент подключается по адресу не из SAN — TLS-хендшейк не проходит, агент соединение
  отвергает (`install.sh` ловит это ещё при настройке).
- Отпечаток CA: в выводе установщика, в панели («Управление агентами») и
  `venv/bin/python3 manage.py ca-fingerprint`. Агент скачивает `ca.crt` с центра
  (`GET /api/v1/ca.crt`) и принимает его только при совпадении отпечатка.
- Обычный HTTP центр не принимает: соединение обрывается.
- **Браузер.** Один раз добавить `ca.crt` в доверенные (сверив отпечаток) — тогда панель
  открывается по `https://<адрес>:<порт>` без предупреждений. Если центр слушает только
  `127.0.0.1` — через SSH-туннель: `ssh -L 8766:127.0.0.1:8766 <хост>`, затем
  `https://127.0.0.1:8766`.
- **Reverse-proxy не нужен.** Если он всё же есть, `configure` спросит о нём и включит доверие
  к `X-Forwarded-*` (`F2B_CENTER_TRUST_PROXY=1`); прокси ходит на центр по `https://` и должен
  доверять `ca.crt`. Без прокси эта опция должна быть выключена — иначе любой клиент может
  подменить свой IP для защиты входа и привязки агента к IP.

## Где что лежит

| Путь | Что |
|---|---|
| `/opt/fail2ban-center/` | код и `venv` |
| `/opt/fail2ban-center/data/f2b-center.sqlite3` | база |
| `/opt/fail2ban-center/data/secret_key` | ключ сессий и HMAC токенов агентов — потеря делает все токены недействительными |
| `/opt/fail2ban-center/data/log_cache/` | лог fail2ban, присланный агентами |
| `/opt/fail2ban-center/data/backup-*.sqlite3` | копии базы, сделанные `update` |
| `/etc/fail2ban-center/tls/` | CA и сертификат |
| `/etc/systemd/system/fail2ban-center.service` | юнит; адреса и порт — в `--bind` |

Логи сервиса: `journalctl -u fail2ban-center -f`.

## Управление из командной строки

`venv/bin/python3 manage.py <команда>` из `/opt/fail2ban-center` от пользователя сервиса:

`create-admin`, `add-agent <имя>`, `list-agents`, `revoke-agent <имя>`,
`regenerate-token <имя>`, `set-event-only <имя> [--off]`, `ca-fingerprint`,
`vpn-init`, `vpn-add-peer <агент> <ключ>`, `init-db`.

## Настройки в панели

- **Протокол агентов** — интервал чекина (60 с), через сколько пропущенных чекинов задача
  считается потерянной.
- **Общий блок-лист** — включение, порог (сколько банов одного IP на одном сервере), срок:
  навсегда или самый долгий `bantime` джейлов сервера.
- **Бан сети Tor** — источник: локальный файл, либо URL (по умолчанию
  `https://check.torproject.org/torbulkexitlist`), при необходимости через прокси
  (`socks5h://…`). Обновление раз в сутки или кнопкой на странице «Блок-лист».
- **Просмотр логов** — `выключен`, `локально` (лог присылает агент), `через Graylog`.
- **Graylog** — см. ниже.

## Graylog

Graylog только принимает логи; центр из него только читает лог fail2ban и показывает его на
вкладке «Лог» сервера. Банят джейлы fail2ban на серверах, по логам Graylog центр ничего не
банит. На серверы ничего ставить не нужно.

### В Graylog

1. **Лог fail2ban серверов должен приходить в Graylog** — чем угодно: rsyslog, Graylog Sidecar,
   journald. Пример для rsyslog на сервере (вход Syslog UDP в Graylog):

   ```
   module(load="imfile")
   input(type="imfile" File="/var/log/fail2ban.log" Tag="fail2ban:")
   *.* @graylog.example.org:514;RSYSLOG_SyslogProtocol23Format
   ```

2. **Пользователь для центра:** System → Users → Create user, роль **Reader**.
3. **Доступ к потоку:** Streams → нужный поток (в том числе «All messages») → Share → этот
   пользователь → Viewer. Без этого поиск отвечает 403: роль Reader сама искать не даёт.
4. **Токен:** у этого пользователя Edit tokens → Create token.

### В центре («Настройки» → Graylog)

| Поле | Что указать |
|---|---|
| URL Graylog | адрес веб-интерфейса/API, например `https://graylog.example.org:9000` |
| Проверять сертификат | снять, если у Graylog самоподписанный сертификат |
| API-токен | токен из шага 4 |
| Stream ID | необязательно — искать только в этом потоке |
| Поле с именем хоста | поле сообщения, где имя сервера: обычно `source`; если там IP сборщика — например, `hostname` |
| Как отличить сообщения fail2ban | фильтр Graylog, см. таблицу ниже |

Затем «Проверить подключение»: центр покажет версию Graylog, сколько сообщений fail2ban нашлось
за сутки, с каких хостов и какие из них не совпали ни с одним агентом. И включить «Просмотр
логов» → «через Graylog».

**Как подобрать фильтр.** Найдите в поиске Graylog строку fail2ban (`"Ban"` или `"Found"`),
раскройте её и посмотрите поля:

| Что видно в сообщении | Фильтр |
|---|---|
| поле `application_name: fail2ban` (syslog RFC 5424, rsyslog с тегом) | `application_name:fail2ban*` (по умолчанию) |
| программы в отдельном поле нет, строка целиком в `message`: `… mail1 fail2ban.actions[…]: …` | `message:fail2ban.* AND NOT message:fail2ban.service` |
| поле пути к файлу (Sidecar/Filebeat) | `filebeat_log_file_path:"/var/log/fail2ban.log"` |
| journald: `_SYSTEMD_UNIT: fail2ban.service` | `_SYSTEMD_UNIT:"fail2ban.service"` |

Проверить фильтр удобно прямо в поиске Graylog: `hostname:"mail1" AND (<фильтр>)` — должны
остаться только строки fail2ban. Поиск по слову `fail2ban` без поля не подходит: он захватывает
строки systemd («Started Fail2Ban Service»), audit и sudo.

**Имя хоста.** Значение поля с именем хоста сравнивается с именем агента. Если они отличаются
(агент `web1`, а в Graylog `web1.example.org`) — в настройках агента («Управление агентами» →
«изменить») заполните «Имя хоста в Graylog».

**Если сервер не шлёт лог в Graylog** (или Graylog недоступен), вкладка «Лог» показывает лог
fail2ban, прочитанный агентом с самого сервера, с пометкой об этом.

## Интеграции, которые только шлют события

SIEM/IDS может сама сообщать о банах: `POST https://<центр>/api/v1/event` с заголовком
`Authorization: Bearer <токен агента>` и телом `{"jail": "...", "ip": "...", "event": "ban"}`.
Такому агенту чекины не нужны — пометьте его `manage.py set-event-only <имя>`: задачи и общие
баны ему не ставятся, `last_seen` обновляется по событиям. Клиент интеграции должен ходить
по `https://` и доверять `ca.crt` центра (для curl — `--cacert`).

## На что обратить внимание

- **`--workers 1` не менять.** Фоновый планировщик (TTL игнора, потерянные задачи, Tor) живёт в
  потоке процесса; параллельность — через `--threads`.
- **Адрес центра, по которому обращается агент, должен быть в сертификате (SAN).** Это адрес
  центра, не агента. Добавление нового агента серт не перевыпускает; новый адрес центра —
  `install.sh configure` (см. «HTTPS и сертификат»).
- **Антивирусы с проверкой HTTPS** на серверах (Dr.Web SpIDer Gate и т. п.) подменяют
  сертификат центра, и агент такое соединение отвергает — см. `agent/README.md`.
- **Часы** центра и серверов должны идти верно (NTP): по времени считаются TTL игнора и
  разбор банов.
- Обновление кода — только через `install.sh update`: он делает копию базы и применяет
  изменения схемы.
