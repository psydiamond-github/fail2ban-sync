# БД центра — SQLite

Реализация модели данных из `docs/TZ.md` (§7 и связанные разделы). Прямой SQL, без ORM —
тот же подход, что и в референсном SSH-проекте.

## Применение

```bash
mkdir -p data
sqlite3 data/f2b-center.sqlite3 < center/db/schema.sql
sqlite3 data/f2b-center.sqlite3 < center/db/seed.sql
```

Оба файла идемпотентны (`IF NOT EXISTS` / `INSERT OR IGNORE`) — безопасно применять повторно
поверх уже существующей БД при обновлении.

При открытии соединения из кода **обязательно** выставлять `PRAGMA foreign_keys = ON;` —
это per-connection настройка SQLite, в файле схемы она не сохраняется между подключениями.

## Отступление от ТЗ, обнаруженное при проектировании схемы

**§5.2 / §3.3 — формат `new_bans`/`new_unbans` в теле чекина.** В ТЗ приведён пример
```json
"new_bans": {"sshd": ["1.2.3.4"]}
```
— голый список IP-строк, без метки времени на каждый адрес. Но дедупликация `agent_events`
(§3.3, "дедуплицируется центром по `(agent_id, jail, ip, since)`") требует `since` на КАЖДЫЙ
факт бана, иначе один и тот же бан, пришедший сначала через `/api/v1/event`, а затем ещё раз
диффом в обычном чекине, не опознаётся как один и тот же случай (нечего сравнивать с `since`
события).

Схема (`agent_events.since NOT NULL`, часть `UNIQUE`) требует протокол в следующем виде:
```json
"new_bans":   {"sshd": [{"ip": "1.2.3.4", "since": "2026-08-19T10:00:00Z"}]},
"new_unbans": {"webui-permanent-ban": [{"ip": "9.9.9.9", "since": "2026-08-19T10:05:00Z"}]}
```
Агент и так знает момент, когда заметил изменение локально (либо берёт его из
`fail2ban-client ... --with-time`) — передать его вместе с IP не требует дополнительной
логики, только расширение формы JSON. Соответствующую правку стоит внести и в сам `docs/TZ.md`
(§5.2) при следующей правке протокола.

## Особенность архитектуры, упрощающая схему относительно SSH-референса

В исходном проекте для подсчёта порога глобального блок-листа требовалась таблица-снимок
`ip_ban_seen` (что было забанено на прошлом опросе по SSH), чтобы отличить новый эпизод бана
от уже известного непрерывного. В агентской модели эта дельта уже посчитана **агентом
локально** перед отправкой (`new_bans` — по определению то, что появилось нового) — отдельный
снимок на стороне центра не нужен, `ip_ban_counters` инкрементируется прямо по строкам
`agent_events(kind='ban')`.
