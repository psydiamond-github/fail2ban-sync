# fail2ban-center: как устроено

Техническое описание для тех, кто сопровождает код: компоненты, протокол, логика
синхронизации, безопасность и места, где легко ошибиться.

## Компоненты

| Где | Что | Код |
|---|---|---|
| центр | Flask-приложение под gunicorn (`--workers 1 --threads 4`), TLS в gunicorn | `center/app.py` (веб), `center/api.py` (API агентов) |
| центр | бизнес-логика протокола и действий из панели | `center/tasks.py` |
| центр | SQLite без ORM, схема и значения по умолчанию | `center/db.py`, `center/db/schema.sql`, `center/db/seed.sql` |
| центр | фоновый поток раз в 30 с: TTL временного игнора, потерянные задачи, обновление Tor раз в сутки | `center/scheduler.py` |
| центр | чтение логов из Graylog | `center/graylog_client.py` |
| центр | отпечаток и выдача CA | `center/center_ca.py` |
| центр | установка, сертификаты, юнит | `center/deploy/install.sh`, `generate-internal-ca.sh`, `fail2ban-center.service` |
| центр | WireGuard-хаб (по желанию) | `center/vpn.py`, `deploy/f2b-center-vpn-helper.sh` |
| сервер | агент: один чекин за запуск | `agent/f2b-agent-checkin.py` |
| сервер | root-обёртка над `fail2ban-client` | `agent/f2b-agent-helper.sh` |
| сервер | отправка мгновенных уведомлений | `agent/f2b-agent-notify.py`, `deploy/f2b-agent-notify.{path,service}` |
| сервер | установка и обновление | `agent/install_agent.sh` |

Центр сам никуда не подключается, кроме Graylog и источника списка Tor. Всё общение с
серверами начинают агенты.

## Протокол агент → центр

Все запросы — HTTPS, `Authorization: Bearer <токен>`. Токен — 256 бит, в базе только
HMAC-SHA256 с ключом `data/secret_key`; привязан к одному агенту.

### `POST /api/v1/checkin` — раз в интервал

```json
{
  "agent_id": "web1", "agent_version": "1.4.0",
  "results": [{"task_id": "t-101", "status": "ok"},
              {"task_id": "t-102", "status": "error", "detail": "..."},
              {"task_id": "t-103", "status": "ok", "data": {"bans": {"sshd": [{"ip": "1.2.3.4", "since": "..."}]},
                                                            "baseline_ignoreip": ["10.0.0.0/8"]}}],
  "new_bans":   {"sshd": [{"ip": "1.2.3.4", "since": "2026-11-12 10:00:00"}]},
  "new_unbans": {"agent-permanent-ban": [{"ip": "9.9.9.9", "since": "..."}]},
  "log_tail": {"path": "/var/log/fail2ban.log", "new_size": 12345, "content": "новые строки"},
  "discovered_jails": [{"name": "sshd", "bantime": 600}]
}
```

Ответ: `{"tasks": [{"task_id": "t-201", "type": "ban", "jail": "sshd", "ip": "5.6.7.8"}]}`.

- `new_bans`/`new_unbans` — разница между текущими банами и прошлым снимком агента. `since`
  у бана — время из `fail2ban-client get <jail> banip --with-time`, у разбана — момент
  обнаружения.
- `discovered_jails` — только обычные джейлы; служебные центр знает сам. Новые джейлы
  добавляются к разрешённым автоматически, пропавшие убираются только по кнопке
  «Пересинхронизировать джейлы».
- Агент сохраняет снимок и результаты только после успешного ответа: при сбое следующий запуск
  отправит то же самое.

### `POST /api/v1/event` — мгновенное уведомление

`{"jail": "sshd", "ip": "1.2.3.4", "event": "ban"}`, ответ 204. Best-effort: тот же факт
придёт и с чекином, центр отбрасывает дубли.

### `GET /api/v1/ca.crt`

Без авторизации — корневой сертификат CA центра. Агент при установке скачивает его без
проверки TLS и принимает только при совпадении SHA-256 отпечатка, полученного из панели.

### Задачи

| `type` | Параметры | На сервере |
|---|---|---|
| `ban` / `unban` | `jail`, `ip` | `fail2ban-client set <jail> banip/unbanip` |
| `ignore_add` / `ignore_del` | `jail`, `ip` | `addignoreip` / `delignoreip`; TTL ведёт центр |
| `permanent_ignore_sync` | `ip_list` | перезапись `jail.d/99-f2b-agent-permanent.local` + `reload` с откатом при ошибке |
| `tor_sync` | `ban_ips`, `unban_ips` | бан/разбан в `agent-tor-block` пачками по 200 адресов |
| `report_full_state` | — | полный список банов по джейлам + базовый `ignoreip` хоста (для показа) |
| `ping` | — | ничего |

Задача, на которую нет результата за `agent_task_stale_after_missed` интервалов, помечается
потерянной. Агенту с `event_only = 1` задачи не ставятся.

## Исполнение на сервере

- Агент работает от `f2b-agent`; к fail2ban — только через `sudo f2b-agent-helper`. Helper
  проверяет каждый аргумент (IPv4, имя джейла по `^[A-Za-z0-9_.-]+$`); агент проверяет то же
  до вызова. Задача с джейлом, которого сейчас нет на хосте, отклоняется агентом, даже если
  пришла от центра.
- Агент обращается только к джейлам, которые есть в `fail2ban-client status`. Запрос к
  отсутствующему джейлу fail2ban пишет в свой лог как ERROR — раньше это давало строку раз
  в минуту.
- Запись `jail.d`-файлов — через временный файл и `install`; если `fail2ban-client reload` не
  прошёл за 5 попыток, файл откатывается.
- Юнит чекина: `ProtectSystem=strict`, запись разрешена в `/var/lib/f2b-agent` и
  `/etc/fail2ban` (туда пишет helper через sudo — пространство имён монтирования общее).
  `NoNewPrivileges` включать нельзя: на нём держится sudo.

### Хук уведомлений

Добавляется к джейлу в памяти fail2ban (`addaction f2b-agent-notify` + `actionban`,
`actionunban`, `actionflush`), файла в `action.d/` нет. После перезапуска fail2ban его
восстанавливает ближайший чекин (`ensure-notify-action` сравнивает команды и меняет только
отличающиеся).

- **С systemd:** `actionban = echo 'ban <jail> <ip>' >> /run/fail2ban/f2b-agent.events`.
  `f2b-agent-notify.path` (`PathModified`) запускает `f2b-agent-notify --flush-spool`: файл
  забирается переименованием, строки отправляются. Причина: под SELinux домену `fail2ban_t`
  запрещены и `systemd-run` (`denied { start } … tclass=system`), и исходящее TCP-соединение
  (`name_connect`); писать в свой `/run/fail2ban` (`fail2ban_var_run_t`) — можно.
  У службы `StartLimitIntervalSec=0` и задержка 1 с перед отправкой: волна банов (общий
  блок-лист, Tor) иначе упирается в лимит запусков systemd, и `.path` уходит в failed
  навсегда.
- **Без systemd:** `setsid f2b-agent-notify ban <jail> <ip> &` — fail2ban после команды убивает
  её группу процессов, голый `&` погиб бы раньше отправки.
- **`actionflush = true`.** Без него при остановке джейла fail2ban вызывает `actionunban` на
  каждый бан, и центр получал сотни «разбанов».
- На `agent-tor-block` хука нет: эти баны ставит центр и знает о них из результата задачи.
- Имя джейла подставляется в команду буквально: тега `<name>` в fail2ban нет.

## Логика центра

### Состояние банов

- `agent_events` — журнал фактов, уникальность `(agent_id, jail, ip, kind, since)`: один бан,
  пришедший уведомлением и чекином, считается один раз.
- `agent_ban_state` — текущие баны для панели. Обновляется событиями, результатами задач и
  целиком — `report_full_state`. При повторном бане с тем же `since` (fail2ban восстановил бан
  после перезапуска) событие отбрасывается как дубль, но `agent_ban_state` обновляется
  всё равно.

### Общий блок-лист

- Счётчик `ip_ban_counters` растёт на каждый новый бан IP на одном агенте (кроме служебных
  джейлов). При достижении порога IP заносится в `global_blocklist` и ставится задача `ban`
  всем активным агентам (кроме `event_only`) — в `agent-permanent-ban` или в джейл с самым
  долгим `bantime`, по настройке. Где применено — `global_block_applied`.
- **Снятие везде:**
  - разбан на сервере в том джейле, куда был применён общий бан, — обнаруживается **только
    чекином** (уведомление о разбане блок-лист не снимает) и снимает IP со всех серверов,
    запись удаляется;
  - разбан из панели на странице сервера — сразу, тем же путём;
  - разбан на странице «Блок-лист» — задачи разбана всем, запись деактивируется.
- **Защита от массового разбана:** больше `MASS_UNBAN_THRESHOLD` (10) разбанов общих IP от
  одного агента за один чекин считается остановкой fail2ban или сбоем, а не действием
  администратора. Блок-лист не трогается, в аудит пишется
  `global_block_mass_unban_ignored`, агенту ставится `report_full_state`.
- Игнор-лист блок-листа (`global_block_ignore`) — сети, которые никогда не попадают в общий
  бан; сети шире /8 не принимаются. Добавление сети/IP не только блокирует будущую эскалацию,
  но и **снимает уже стоящие баны** для попавших адресов (`lift_bans_in_network`): общий
  блок-лист отзывается на всех агентах с забыванием IP, плюс ставятся разбаны для обычных
  джейлов, где адрес сейчас забанен. «Это не бот» → разбанить везде.

### Игноры

- Временный: задача `ignore_add`, запись в `temp_ignore` с `expires_at`; по истечении
  планировщик ставит `ignore_del`.
- Постоянный: центр отправляет (`permanent_ignore_sync`) ТОЛЬКО свои адреса, принимает IPv6
  и сети. Каждый источник `ignoreip` — в своей ИМЕНОВАННОЙ переменной fail2ban (в `[DEFAULT]`),
  итоговый `ignoreip` собирается ПОДСТАНОВКОЙ переменных, а не копированием значений:
    - `f2b_base_ignoreip` — база хоста, живёт в **`jail.local`**, владелец админ. Центр не
      трогает. helper гарантирует, что переменная определена: если её в `jail.local` нет —
      заводит один раз (значение = объединение исторических источников минус адреса центра,
      с дефолтом `127.0.0.0/8`), если есть — не перезаписывает.
    - `f2b_center_ignoreip` — адреса центра, живёт в `jail.d/99-f2b-agent-permanent.local`,
      владелец агент.
  Файл `jail.d/99-…` пишет `ignoreip = %(f2b_base_ignoreip)s %(f2b_center_ignoreip)s` —
  fail2ban интерполирует обе (все `[DEFAULT]` из `jail.local` и `jail.d/` сливаются в одно
  пространство имён). Поэтому: (1) база не теряется и не затирается синхронизацией; (2) админ
  правит базу в `jail.local`, центр её не трогает; (3) `127.0.0.0/8` не пропадает; (4) нужна
  третья переменная (напр. Tor) — добавляется в строку подстановкой. `baseline_ignoreip` в БД
  центра — только для показа в панели (из `base-ignoreip`, читает переменную из `jail.local`),
  в состав записываемого `ignoreip` не входит.
  **Миграция:** старый `jail.d/00-f2b-agent-base.local` (где база жила раньше) при первом
  синке переносится в `jail.local` и удаляется — автоматически, значения сохраняются.

### Tor

Центр раз в сутки (или по кнопке) скачивает список (URL, при необходимости через прокси; или
читает файл), хранит в `tor_exit_nodes` и каждому агенту ставит `tor_sync` с разницей
относительно `tor_block_applied`. Отметка времени пишется и при неудаче — иначе планировщик
повторял бы скачивание каждые 30 с.

### Логи

Агент в каждом чекине присылает новые байты лога fail2ban (`helper log-tail <offset>`, путь из
`fail2ban-client get logtarget`). В режимах `local` и `graylog` центр дописывает их в
`data/log_cache/<agent_id>.log` с ограничением размера.

Режим `graylog`: центр только читает.
- Запрос: `<поле хоста>:"<агент или его graylog_source>" AND (<фильтр сообщений fail2ban>)`
  [`AND "<джейл>"`]. Поле хоста — `graylog_host_field` (по умолчанию `source`), фильтр —
  `graylog_fail2ban_query` (по умолчанию `application_name:fail2ban*`).
- API: `POST /api/views/search/messages` (Graylog 5+, ответ — CSV, `Accept: text/csv`). Ему
  достаточно права на чтение потока, роль Reader подходит. Если ответ 404 (Graylog 4.x) —
  `GET /api/search/universal/relative`: в Graylog 6 он требует права `searches:relative`,
  которого у Reader нет.
- Пустой запрос означает «все сообщения»; `*` новый API отвергает (ведущий wildcard).
- Нет сообщений за период или ошибка Graylog — вкладка показывает лог из кэша центра.
- Токен Graylog хранится только в базе центра; в браузер не попадает, поле формы не
  заполняется обратно.

## Безопасность

- **TLS.** Только HTTPS, свой CA. Агент проверяет сертификат центра по `ca_cert` из конфига
  (не по системному хранилищу) и отказывается работать с `http://`. Установщик агента делает
  пробный TLS-запрос и различает «адреса нет в сертификате» и «сертификат подменён».
- **Токены агентов** — HMAC в базе, показываются один раз. Отзыв — следующий чекин получает 401.
- **Привязка к IP** (`pinned_ip`): `advisory` — запись в аудит, `strict` — чекин отклоняется.
- **Частота чекинов** чаще половины интервала — запись `checkin_rate_anomaly` в аудит, без
  отказа.
- **Веб:** сессия Flask (cookie `Secure`, `HttpOnly`, `SameSite=Strict`), CSRF-токен на всех
  POST, роли проверяются на каждом маршруте, блокировка входа после 10 неудач за 5 минут
  (в памяти процесса, по IP), `X-Frame-Options: DENY`, `nosniff`.
- **`F2B_CENTER_TRUST_PROXY`** включать только за своим прокси: иначе `X-Forwarded-For`
  подделывается клиентом и обходит блокировку входа и `strict`-привязку.
- **sudo на сервере** — только `f2b-agent-helper` без аргументов-шаблонов; helper сам
  проверяет подкоманду и аргументы.

## Модель данных

| Таблица | Что |
|---|---|
| `users` | пользователи панели, роль `admin`/`operator` |
| `agent_groups` | вложенные группы (только навигация) |
| `agents` | агенты: хэш токена, `allowed_jails` (JSON с `bantime`), привязка к IP, `graylog_source`, `baseline_ignoreip`, `event_only`, `revoked_at` |
| `agent_tasks` | очередь задач: `pending` → `delivered` → `done`/`error`/потеряна |
| `agent_events` | журнал банов/разбанов с дедупликацией |
| `agent_ban_state` | текущие баны для панели |
| `permanent_ignore`, `temp_ignore` | игноры |
| `ip_ban_counters`, `global_blocklist`, `global_block_applied`, `global_block_ignore` | общий блок-лист |
| `tor_exit_nodes`, `tor_block_applied` | Tor |
| `agent_log_cache` | позиция в логе fail2ban агента; текст — в `data/log_cache/` |
| `agent_vpn_peers` | WireGuard-пиры |
| `audit_log`, `settings` | аудит, настройки (значения по умолчанию — `seed.sql`) |

`schema.sql` и `seed.sql` идемпотентны (`IF NOT EXISTS`, `INSERT OR IGNORE`); новые столбцы
добавляет `db.init_db()` (`ALTER TABLE`), его вызывает `install.sh update`. В каждом соединении
нужно `PRAGMA foreign_keys = ON` (делает `db.get_conn()`).

## На что обратить внимание в коде

- **Один процесс.** `scheduler.start()` вызывается при импорте `app.py`; несколько воркеров
  запустили бы несколько планировщиков. В тестах планировщик выключен
  (`F2B_CENTER_NO_SCHEDULER=1`), иначе его поток гоняет те же задачи параллельно с тестом.
- **Модули с константами путей.** `db.DATA_DIR` вычисляется при импорте — тесты переимпортируют
  модули на каждый тест (`tests/conftest.py`).
- **Чекбоксы настроек.** Браузер не присылает снятый чекбокс — `admin_settings` выставляет `0`
  для всех чекбоксов, отсутствующих в форме.
- **Большие диффы.** Первый чекин с тысячами банов (Tor) пишется по одной транзакции на бан;
  таймаут запроса агента — 120 с, helper — 30 с, поэтому `tor-sync` идёт пачками.
- **Разбан ≠ ручное действие.** Любая новая логика, реагирующая на разбаны, должна учитывать,
  что fail2ban «разбанивает» при остановке и что джейл бывает недоступен на время перезапуска.
