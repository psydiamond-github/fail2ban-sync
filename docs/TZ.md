# ТЗ: fail2ban-center — централизованное управление fail2ban через агентов

Статус: черновик, проект с нуля.

**Расположение и границы.** Это новый, отдельный проект в репозитории `fail2ban-sync` —
код пишется заново, своей кодовой базой, не поверх существующего. Исходный SSH-based
`fail2ban-webui` (директория `webui/` в этом же репозитории, а также независимо развивающийся
проект в `fail2ban-sync-host`) **не модифицируется и не используется как зависимость** — оба
служат только референсом: откуда брать проверенные UI-решения (шаблоны, разметка страниц,
структура настроек) и уже реализованные там фичи (роли admin/operator, группы серверов,
логика глобального блок-листа, постоянный/временный игнор, бан сети Tor) как функциональный
эталон при проектировании этого проекта — не как код для повторного использования и не как
основа для расширения. Транспорт (SSH) из референсных проектов не переносится вообще —
это единственное принципиальное архитектурное отличие нового проекта.

## 1. Назначение

Веб-панель для просмотра и управления банами fail2ban на произвольном числе серверов из одного
места, без необходимости входящего доступа (SSH или любого другого) с центра на управляемые
хосты. Каждый управляемый хост сам инициирует соединение с центром — актуально для серверов за
NAT/CGNAT, за файрволом с закрытыми входящими портами, без белого IP.

Реалтайм не требуется — базовый интервал синхронизации 60 секунд (настраиваемый), с отдельным
быстрым событийным каналом для ускорения реакции кросс-серверного блок-листа.

## 2. Термины

| Термин | Значение |
|---|---|
| **Центр** | Сервер управления — веб-интерфейс, БД, REST API для агентов |
| **Агент** | Процесс на управляемом хосте, исполняет команды через `fail2ban-client`, сам инициирует связь с центром |
| **Чекин** | Периодический опрос агентом центра — отчёт о состоянии + получение новых задач |
| **Задача (task)** | Единица работы, поставленная центром в очередь конкретного агента |
| **Джейл** | Джейл fail2ban на управляемом хосте, из **фиксированного, заданного при регистрации списка** |

## 3. Функциональные требования

### 3.1. Управление банами
- Просмотр списка забаненных IP по каждому джейлу каждого сервера (с точностью до последнего
  успешного чекина — не live).
- Ручной бан IP в выбранном джейле (роль **admin**).
- "Забанить навсегда" — служебный джейл с `bantime = -1` на управляемом хосте (тот же принцип,
  что и в исходном проекте).
- Разбан IP в любом джейле (**admin** и **operator**).

### 3.2. Игнор-листы
- **Временный игнор** — `addignoreip` с TTL, ведётся центром, реконсиляция каждым чекином (если
  агент обнаружил, что runtime-игнор пропал после рестарта fail2ban на хосте — восстанавливает).
- **Постоянный игнор** — персистентный, пишется агентом в jail.d-конфиг, объединяется с уже
  настроенным администратором сервера `[DEFAULT] ignoreip` (замещение всего значения, не патч —
  тот же компромисс, что и в исходном проекте, с показом обоих списков раздельно в UI).

### 3.3. Глобальный блок-лист
- Если один IP банится на одном сервере N раз подряд (порог настраивается) — банится сразу на
  всех агентах.
- "Липкая" память — повторное появление ранее разбаненного вручную IP снова банит его везде.
- Приоритет за ручными действиями администратора на самом сервере: если бан снят
  непосредственно на хосте (не через центр) в служебном джейле блок-листа — центр это
  обнаруживает и разбанивает IP везде, полностью забывая его.
- Игнор-лист блок-листа ("это не бот") — сети/IP, которые никогда не попадают под
  автообнаружение, с проверкой на охват уже существующими записями, импортом/экспортом.
- Требует от протокола не только `new_bans` (появившиеся баны), но и **`new_unbans`** —
  агент должен репортить и пропавшие баны в джейле блок-листа, иначе центр не узнает о ручном
  разбане на месте (см. §6.2).

### 3.4. Бан сети Tor (опционально)
- Список exit-нод скачивается **центром** (упрощение относительно исходного проекта — там
  скачивание делегировалось одному из управляемых серверов из-за недоступности источника с
  части хостов; в агентской модели логичнее тянуть список централизованно и раздавать всем
  агентам одной задачей).
- Раз в сутки или по кнопке — диффом (только новые/выпавшие) через задачу `tor_sync`.

### 3.5. Группы серверов
- Произвольная вложенность, чисто навигационная фича, не связана с транспортом — переносится
  без изменений.

### 3.6. Пользователи и роли
- **admin** — всё, включая пользователей/агентов/группы/настройки, ручной бан.
- **operator** — просмотр, разбан, временный игнор. Банить не может.
- Нельзя понизить/удалить последнего admin. Смена роли — с подтверждением.

### 3.7. Аудит-лог
- Каждое действие (создание задачи, применённая на агенте задача, зарегистрированное событие) —
  запись в аудит с указанием инициатора (пользователь либо сам агент/планировщик).

### 3.8. Настройки
- Интервал чекина по умолчанию, порог/срок глобального блок-листа, параметры Tor-бана,
  параллелизм массовых операций (рассылка задачи сразу многим агентам).

### 3.9. Просмотр логов

Настройка `log_view_mode`: `none` (выключено), `local` или `graylog`.

**`local`** — сам агент на каждом обычном чекине докачивает только новые байты лога fail2ban
(`f2b-agent-helper log-tail <offset>`, путь — динамически из `fail2ban-client get logtarget`),
центр дописывает их в свой локальный файл-кэш (`data/log_cache/<agent_id>.log`, с обрезкой по
верхней границе размера) и показывает на вкладке "Лог". Ничего внешнего разворачивать не
нужно — работает сразу после установки агента, ценой того, что размер кэша растёт на диске
центра. Поле `log_tail` присутствует в теле каждого checkin независимо от того, включён ли
режим — стоимость пустого хвоста (пара строк) пренебрежимо мала, а согласовывать с агентом
текущий режим центра отдельным round-trip'ом не требуется.

**`graylog`** — логи собираются во внешний **Graylog**, не через агентский канал (это
отдельная, гораздо более тяжёлая нагрузка, для которой Graylog — правильный инструмент;
дублировать её через раз-в-минуту чекин бессмысленно). На стороне Graylog нужно:
1. Создать вход (System → Inputs) типа **GELF TCP**, `use_null_delimiter=true`, и убедиться,
   что порт проброшен наружу именно как TCP (не UDP — тип входа и проброс порта должны
   совпадать, иначе сообщения молча теряются).
2. Завести отдельного пользователя с ролью Admin — не встроенный root/admin (в некоторых
   версиях Graylog персональные токены для встроенного суперпользователя не выпускаются) — и
   выпустить ему Personal Access Token (System → Users → пользователь → Tokens).
3. На каждом управляемом хосте — форвардер, шлющий строки лога fail2ban в этот вход по GELF
   TCP с полем `host` = имени агента (для сопоставления с `graylog_source`, см. ниже); готовый
   скрипт — `agent/f2b-log-forward-gelf.py` (опциональный компонент, не часть обязательной
   установки агента).

Центр **сам** обращается к Graylog REST API напрямую (обычная интеграция "центр → внешняя
система", не связанная с агентским протоколом) и показывает результат во вкладке "Лог":

- **Запрос к Graylog** — `GET /api/search/universal/relative` (или `/absolute` для явного
  диапазона времени) с параметром `query`, например:
  `source:"<hostname_агента>" AND (program:"fail2ban" OR facility:"fail2ban")`, `range` — окно
  времени (по умолчанию последние 24 часа, с возможностью выбрать другое в UI), `sort=timestamp:desc`.
- **Сопоставление хоста агента и поля Graylog `source`** — не всегда совпадает один в один
  с `agents.name` (зависит от того, как настроен forwarder на хосте) — у агента в БД центра
  добавляется необязательное поле `graylog_source` (если не задано — используется `agents.name`
  как значение по умолчанию).
- **Фильтр по джейлу** — дополнительный текстовый фильтр в UI (`AND message:"<jail>"` к
  запросу) — сузить вывод до конкретного джейла, без пересборки сложного запроса руками.
- **Пагинация/лимит** — Graylog API поддерживает `limit`/`offset` — в UI страница выдаёт
  разумное количество строк (например, 300, как было в исходном проекте) с возможностью
  "показать ещё" вместо выгрузки всей истории разом.
- **Ссылка "Открыть в Graylog"** — рядом с встроенным выводом вкладка отдаёт готовую ссылку на
  сам Graylog UI с тем же query и диапазоном — если администратору нужны полные возможности
  Graylog (сохранённые поиски, дашборды, корреляция с другими источниками), не дублировать их
  в своём UI.

**Аутентификация к Graylog** — API-токен (Graylog поддерживает токен как логин при Basic
Auth, пароль — литерал `token`), настраивается в разделе "Настройки" центра (URL инстанса,
токен, опционально — конкретный `stream_id`, если логи fail2ban выделены в отдельный поток).
Токен — секрет уровня БД центра, не отдаётся браузеру ни в каком виде: все запросы к Graylog
идут **только с backend** центра, UI получает от центра уже готовый JSON/HTML результата, а не
прямой доступ к Graylog API.

**Права доступа** — вкладка "Лог" видна и `admin`, и `operator` (только просмотр, как и
остальные read-only разделы) — сам Graylog-токен при этом не раскрывается ни той, ни другой
роли, поскольку запрос идёт через backend.

**Отказоустойчивость** — если Graylog недоступен или не настроен (пустой URL/токен в
настройках) — вкладка "Лог" показывает понятное сообщение, не ломает остальную страницу
сервера; это дополнительная, не критичная для основной функциональности часть UI.

### 3.10. Сознательно вне рамок проекта
- **SSH-транспорт и джамп-хосты** — не поддерживаются в этой системе; хосты, недостижимые
  через исходящий HTTPS от агента, вне охвата проекта.
- **Реалтайм** (WebSocket/live-обновление UI) — не требуется, интерфейс отображает состояние на
  момент последнего чекина.
- **Собственное хранение/ротация логов** — полностью делегировано Graylog (см. §3.9), центр не
  хранит сырые логи хостов у себя.

## 4. Архитектура

```
 [Агент 1] --HTTPS(исходящий)--\
 [Агент 2] --HTTPS(исходящий)--- [Центр: REST API + БД + Web UI] <-- браузер администратора
 [Агент N] --HTTPS(исходящий)--/
```

- Центр **не открывает соединений к агентам** — только слушает входящие HTTPS-запросы (за
  nginx+TLS, как терминирующий reverse-proxy).
- Каждый агент раз в интервал (по умолчанию 60 с) делает `POST /api/v1/checkin` — отчитывается
  о выполненных задачах и новых событиях, получает в ответ следующую порцию задач.
- Дополнительно — событийный канал `POST /api/v1/event`, вызываемый fail2ban'ом хоста сразу в
  момент бана/разбана (через `action.d`-хук), для быстрой реакции блок-листа без ожидания
  следующего чекина.
- Центр сам управляемым хостом (если веб-панель крутится на сервере, который тоже нужно
  администрировать) не является особым случаем — на него ставится тот же агент, что и на любой
  другой хост, указывающий на `https://localhost` или адрес самого центра. Отдельного
  "локального" транспорта, в отличие от исходного проекта, не требуется.

## 5. Протокол обмена

### 5.1. Аутентификация
`Authorization: Bearer <token>` на каждом запросе. Токен — 256 бит случайности, выдаётся при
регистрации агента в UI центра, в БД хранится **только хэш** (HMAC-SHA256), скоуплен на
конкретный `agent_id` — компрометация одного токена не даёт доступа к данным/задачам других
агентов. Обязательно только через HTTPS.

### 5.2. `POST /api/v1/checkin`

Запрос (агент → центр):
```json
{
  "agent_id": "srv-42",
  "agent_version": "1.0.0",
  "results": [
    {"task_id": "t-101", "status": "ok"},
    {"task_id": "t-102", "status": "error", "detail": "джейл не найден"},
    {"task_id": "t-103", "status": "ok", "data": {"bans": {"sshd": [{"ip": "1.2.3.4", "since": "..."}]}, "baseline_ignoreip": ["10.0.0.0/8"]}}
  ],
  "new_bans":   {"sshd": [{"ip": "1.2.3.4", "since": "2026-08-19T09:58:00Z"}]},
  "new_unbans": {"agent-permanent-ban": [{"ip": "9.9.9.9", "since": "2026-08-19T10:00:00Z"}]}
}
```
`new_bans`/`new_unbans` — списки ОБЪЕКТОВ `{"ip", "since"}` на каждый джейл, не голых строк
(уточнение к первоначальному черновику протокола — см. приложение A). `results[].data` —
опционально, структурированный результат задачи (сейчас используется только
`report_full_state`, см. приложение A, п.2).

Ответ (центр → агент):
```json
{
  "tasks": [
    {"task_id": "t-201", "type": "ban",  "jail": "sshd", "ip": "5.6.7.8"},
    {"task_id": "t-202", "type": "ignore_add", "jail": "sshd", "ip": "9.9.9.9", "ttl": 3600}
  ]
}
```

### 5.3. `POST /api/v1/event` — быстрое уведомление
```json
{"jail": "sshd", "ip": "1.2.3.4", "event": "ban", "since": "2026-08-19T10:00:00Z"}
```
Ответ 200/204 без тела. Best-effort: если не доставлено — тот же факт всё равно попадёт в
`new_bans`/`new_unbans` следующего обычного чекина, дедуплицируется центром по
`(agent_id, jail, ip, kind, since)`.

### 5.4. Типы задач

| `type` | Параметры | Действие на агенте |
|---|---|---|
| `ban` | `jail`, `ip` | `fail2ban-client set <jail> banip <ip>` |
| `unban` | `jail`, `ip` | `fail2ban-client set <jail> unbanip <ip>` |
| `ignore_add` | `jail`, `ip`, `ttl` | `addignoreip`, TTL ведёт центр |
| `ignore_del` | `jail`, `ip` | `delignoreip` |
| `permanent_ignore_sync` | `ip_list` (готовый merged-список) | перезапись jail.d-файла + `reload` |
| `tor_sync` | `ban_ips`, `unban_ips` | diff-бан/разбан в служебном джейле |
| `report_full_state` | — | полный список банов по каждому джейлу (не дифф) — после потери синхронизации/для нового агента |
| `ping` | — | без действия, обновляет `last_seen` |

### 5.5. Идемпотентность
- Каждая задача имеет уникальный `task_id`; повторная доставка одного и того же ответа
  `checkin` (например, после сетевого сбоя) не должна привести к повторному исполнению — агент
  и центр сверяются по `task_id`.
- Задачи, на которые не пришёл `result` в разумный срок (несколько пропущенных чекинов),
  помечаются центром как потерянные и отображаются в UI как требующие внимания.

## 6. Исполнение команд на агенте

- Агент — непривилегированный процесс. Все операции над fail2ban — только через
  `sudo /usr/local/sbin/f2b-agent-helper <подкоманда>`, аналогично проверенной модели исходного
  проекта: узкое sudoers-правило на один конкретный root-скрипт, двойная валидация аргументов
  (IPv4/имя джейла) — на стороне агента и внутри самого скрипта.
- Список разрешённых джейлов — статичен, задаётся один раз при регистрации агента, хранится в
  локальном конфиге. Любая задача с джейлом вне этого списка отклоняется агентом безусловно,
  даже если она пришла с валидной авторизацией от центра — вторая граница защиты на случай
  ошибки/компрометации центра.
- Агент запускается как `systemd timer` (не постоянный демон, не cron) — каждый тик:
  чекин → выполнение полученных задач → следующий тик отправляет их результаты.

### 6.1. Событийный хук уведомления
- Реализовано **чисто runtime**, без физического файла в `action.d/` (сознательное
  уточнение при реализации — см. приложение A, п.4): `fail2ban-client set <jail> addaction
  f2b-agent-notify`, затем `set <jail> action f2b-agent-notify actionban/actionunban <cmd>` —
  добавляется К уже настроенному `action` джейла, не замещает его.
- Именно поэтому не переживает `restart` fail2ban — состояние только в памяти
  `fail2ban-server`; агент на каждом чекине проверяет наличие хука
  (`fail2ban-client get <jail> actions`) и восстанавливает при необходимости
  (`ensure-notify-action` в `f2b-agent-helper`, дешёвая проверка — фактическая
  переустановка происходит только если хука ещё нет).
- Сам вызов `f2b-agent-notify` исполняется от root (контекст самого fail2ban), sudo не
  требуется; короткий таймаут, фоновый запуск (`&` в теле command), ошибка сети не должна
  тормозить обработку следующих банов.

## 7. Модель данных центра

- **`agents`** — `id`, `name`, `token_hash`, `allowed_jails` (JSON), `pinned_ip` (nullable,
  advisory), `last_seen`, `group_id`, `created_at`, `graylog_source` (nullable — см. §3.9,
  если поле Graylog `source` не совпадает с `name`).
- **`agent_tasks`** — `id`, `agent_id`, `type`, `payload` (JSON), `status`
  (`pending`/`delivered`/`done`/`error`), `created_at`, `delivered_at`, `result_detail`.
- **`agent_events`** — журнал `new_bans`/`new_unbans`/`event`, с дедупликацией по
  `(agent_id, jail, ip, since)`.
- **`global_blocklist`**, **`global_block_ignore`** — логика как в исходном проекте, источник
  данных — `agent_events`, а не прямой опрос по SSH.
- **`groups`**, **`users`**, **`audit_log`** — без изменений по смыслу относительно исходного
  проекта.
- **`settings`** — как в исходном проекте, плюс `log_view_mode` (`none`/`local`/`graylog`),
  `graylog_url`, `graylog_api_token` (секрет, не отдаётся в API/UI), `graylog_stream_id`
  (опционально).
- **`agent_log_cache`** — `agent_id`, `path`, `offset_pos`, `updated_at`: позиция в логе
  fail2ban, докачанная агентом (режим `local`, §3.9); сам текст — в файле на диске, не в БД.

## 9. Установка и эксплуатация

### 9.1. Центр
- Единый Python/Flask-процесс за gunicorn (по образцу исходного проекта), SQLite, systemd-юнит.
- Слушает только на loopback, снаружи — через nginx с TLS (обязательно, не опция).

### 9.2. Регистрация и установка агента
1. В UI центра — "добавить агента": ввод имени, выбор разрешённых джейлов → генерируется
   `agent_id` + токен, показывается готовая команда установки.
2. На хосте — install-скрипт выполняется **вручную**, локально, кем угодно с root-доступом:
   кладёт helper + sudoers-правило + токен (`root:root`, `chmod 600`) + сам агент-скрипт +
   `systemd timer`. Удалённого автопровижининга и временного passwordless-sudo, в отличие от
   SSH-модели исходного проекта, не требуется вообще — это чище: центру никогда не нужен
   административный доступ к хосту.

### 9.3. Обновление
- Обновление центра — как в исходном проекте (rsync + restart).
- Обновление агента — заменить скрипт на хосте, `systemctl restart` таймера/следующий тик
  подхватит новую версию. Версионирование протокола (`agent_id` в запросе может сопровождаться
  версией агента) — на случай будущих несовместимых изменений API.

### 9.4. Отзыв агента
- Удаление/инвалидация записи в `agents` на центре — следующий чекин получает 401. Доступ к
  самому хосту центру не нужен.

## 10. Безопасность

- Токен — 256 бит, хэш в БД, скоуп на один `agent_id`.
- TLS обязателен для всех обращений к API центра.
- Привязка к IP — advisory (алерт в UI при чекине с нового адреса), не hard-reject по
  умолчанию — из-за плавающих/общих IP у типичных NAT/CGNAT-хостов, ради которых и делается
  этот транспорт; жёсткий reject — опционально, per-agent, для хостов со статическим IP.
- Rate-limit на центре: чекин ожидается не чаще заданного интервала — аномально частые
  обращения с одним токеном логируются как подозрительные.
- Модель привилегий на агенте не меняется относительно исходного проекта — root-доступ у
  агента нет, всё идёт через один фиксированный скрипт с сузженным sudoers.
- **Graylog API-токен** (см. §3.9, §7) хранится только в БД центра, никогда не передаётся в
  браузер — запросы к Graylog идут исключительно с backend центра, UI получает уже готовый
  результат. Компрометация токена конкретного агента не даёт доступа к Graylog (разные
  секреты, разные каналы).

## 11. Нефункциональные требования

- Задержка применения ручного действия (бан/разбан из UI) — до одного интервала чекина
  (по умолчанию до 60 с) плюс задержка события, если применимо; асинхронность и её отображение
  в UI ("поставлено в очередь", `last_seen`, статус последней задачи) — часть UX по дизайну,
  не недостаток.
- Число агентов — ограничено в первую очередь пропускной способностью центра принимать
  чекины (простые insert/update в SQLite на каждый запрос) — на порядок выше, чем текущий
  предел исходного проекта (там — последовательный обход по SSH раз в 60 с).

## 12. Технологический стек (предложение)

- Python 3 + Flask + gunicorn — центр (переиспользование опыта исходного проекта).
- SQLite — единственное хранилище на центре, без ORM, без очередей задач (Celery/RQ) — объём
  и характер нагрузки не оправдывают.
- Агент — bash или Python (без тяжёлых зависимостей, только `curl`/`requests`), `systemd timer`.
- Интеграция с Graylog — обычные HTTP-запросы к его REST API с backend центра (`requests`),
  без отдельного SDK/клиента — Graylog API самодостаточен через `GET`-запросы с Basic Auth.
- nginx — TLS-терминация перед центром.

## 13. Этапы реализации

1. **MVP** — регистрация агента, `checkin` с `ban`/`unban`/`ping`, UI просмотра списка банов и
   ручного бан/разбан по джейлу, роли admin/operator, установка центра+агента.
2. **v2** — временный/постоянный игнор, глобальный блок-лист (`new_bans`/`new_unbans`,
   пороговая логика, липкая память, игнор-лист блок-листа), группы серверов.
3. **v3** — событийный канал уведомления (runtime-хук через `addaction`, §6.1), бан сети Tor, аудит-лог,
   тонкая настройка интервалов/rate-limit, отображение аномалий IP-привязки в UI, интеграция
   просмотра логов через Graylog (§3.9).

## 14. Критерии приёмки (для MVP)

- Агент, запущенный на хосте без входящих портов (только исходящий HTTPS), успешно
  регистрируется, проходит чекин и исполняет тестовый бан/разбан.
- Компрометация токена одного агента не даёт доступа к задачам/данным другого (проверяется
  тестом на скоуп токена).
- Отключение/удаление агента в UI останавливает исполнение новых задач для него без каких-либо
  действий на самом хосте.
- Ручной бан из UI отражается в статусе задачи и применяется на хосте в пределах одного
  интервала чекина.

## 15. Приложение A: уточнения протокола, сделанные при реализации

ТЗ выше — проектный документ, писавшийся до кода. При реализации (`center/`, `agent/` в
этом репозитории) обнаружилось несколько мест, требующих уточнения относительно того, как
исходно описано в разделах 1-14. Каждое отражено и в самом коде (комментариями с пометкой
"см. приложение A"), и здесь — как сводка.

1. **Формат `new_bans`/`new_unbans` (§5.2, §3.3).** Изначальный пример показывал голый
   список IP-строк на джейл. Дедупликация `agent_events` по `(agent_id, jail, ip, kind,
   since)` требует `since` на КАЖДЫЙ факт, иначе одно и то же событие, пришедшее сначала
   через `/api/v1/event`, а затем диффом в обычном чекине, не опознаётся как один и тот же
   случай. Исправлено на список объектов `{"ip", "since"}` — см. актуальный пример в §5.2.

2. **Поле `data` в `results[]` (§5.2).** Не было предусмотрено, как `report_full_state`
   возвращает СОБСТВЕННО данные (список банов + baseline ignoreip) — в исходном протоколе
   `results[]` нёс только `status`/`detail`. Добавлено необязательное поле `data`: для
   `report_full_state` — `{"bans": {jail: [{"ip","since"}]}, "baseline_ignoreip": [ip, ...]}`.
   `baseline_ignoreip` кэшируется в `agents.baseline_ignoreip` (новое поле в схеме, §7) — без
   него `permanent_ignore_sync` не мог бы пересобрать merged-список (§3.2), поскольку в
   pull-модели нет способа синхронно прочитать `[DEFAULT] ignoreip` с агента по требованию.

3. **`allowed_jails` несёт метаданные, не только имена (§5, §6, §7).** Формат —
   `[{"name": "sshd", "bantime": 600}, ...]`, не список строк. Нужно для режима
   `global_block_duration_mode = longest_jail_bantime` (упомянут в §3.3/настройках, но
   протокол не предусматривал способа узнать bantime джейла с агента) — раз джейлы и так
   статичны и задаются администратором при регистрации, bantime указывается там же, без
   отдельного "прочитать с агента" запроса.

4. **`agent-permanent-ban` и `agent-tor-block` — не отдельные задачи протокола.**
   - `agent-permanent-ban` (bantime=-1, для "забанить навсегда" и части сценариев
     глобального блок-листа) добавляется в `allowed_jails` АВТОМАТИЧЕСКИ центром при
     регистрации агента (администратор не выбирает его вручную) и провижинится install-
     скриптом на хосте один раз при установке — постоянный jail.d-файл, переживает restart.
   - `agent-tor-block` создаётся лениво и идемпотентно ВНУТРИ обработчика задачи `tor_sync`
     на стороне агента (`f2b-agent-helper tor-sync` сам проверяет/создаёт джейл перед
     применением диффа) — отдельного типа задачи `ensure_tor_jail` в протоколе нет.
   - Хук быстрого уведомления (§6.1) реализован ЧИСТО runtime (`addaction` + `action ...
     actionban/actionunban`), без физического файла в `action.d/` — соответственно не
     переживает `restart`, требует проверки на каждом чекине (см. правку §6.1).

5. **Rate-limit (§10) реализован как soft-предупреждение, не hard-reject.** Чекин чаще
   половины настроенного интервала логируется в аудит как аномалия (`checkin_rate_anomaly`),
   но не отклоняется — в отличие от `ip_pin_mode=strict`, который реально блокирует запрос.

Ничего из этого не меняет архитектурные решения разделов 1-14 — только форму протокола и
разделение ответственности "что статично при регистрации" / "что вычисляется на лету".
